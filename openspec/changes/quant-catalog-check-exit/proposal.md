# A check whose exit code is discarded is not a gate

## Why

`make check-quant-catalog` is green on a stale table and cannot be red (issue #701). The generator's
`main()` returns 1 when the committed table differs from what it produces, and its `__main__` discards it:

```python
if __name__ == "__main__":
    main()
```

Measured on `main` @ `3e63bb3`:

```
$ make check-quant-catalog ; echo "exit=$?"
FAIL: data/trending-quant-catalog.json is stale (run make sync-quant-catalog)
--- committed
+++ generated
@@ -1570,127 +1570 @@
-  { "repo": "ddalcu/Qwen3.8-Flash-Next-MLX-Serve-mixed-4-8bit", ... }
exit=0
```

Two places believe that exit code: `make ci-unit` (every PR) and the `registry-sync` job's step 9, which
runs `check-quant-catalog` before `test-unit`. A stale HF class table — the one `llgenie --pick` reads to
resolve a quant file — has been shipping through both.

## What changes

1. **`raise SystemExit(main())`** in `scripts/gen_trending_quant_catalog.py`, so the staleness reaches
   `make` and CI.
2. **Regenerate the table it was hiding**: `make sync-quant-catalog` (the committed copy predates the live
   Hub — `ddalcu/Qwen3.8-Flash-Next-MLX-Serve-mixed-4-8bit` no longer resolves, so the generator no
   longer lists it).
3. **A guard against the class**: `tests/test_script_exit_codes.py` walks `scripts/*.py` and, for any
   `__main__` block that calls `main()` bare, requires `main()` never `return`s a value. That is the
   defect exactly — a discarded status. `scripts/llgenie_serve.py` also calls `main()` bare and is fine,
   because its `main()` returns `None`; the guard says so instead of failing it.

## Impact

- `scripts/gen_trending_quant_catalog.py` — the `__main__` block.
- `data/trending-quant-catalog.json`, `tests/fixtures/trending-quant-catalog.json` — regenerated by the
  committed generator, no hand edits.
- `tests/test_script_exit_codes.py` — new, discovered by `make test-unit` with no roster edit (the suite is
  aggregated, AGENTS.md).
- `Makefile` unchanged: `check-quant-catalog` already invokes the script; it just gets a real status now.

Not in this change: why upstream stopped serving that repo (the sync's business, #677/#687), and the
registry sync landing (#669/#677).
