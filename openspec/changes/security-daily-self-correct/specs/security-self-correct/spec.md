## ADDED Requirements

### Requirement: The scan is its own pipeline, never a PR or push check

`.github/workflows/security-scan.yml` MUST trigger only on its own `schedule` and
`workflow_dispatch`. It MUST NOT carry a `pull_request:` or a `push:` trigger, so a pre-existing
advisory can never red a pull request or a push to `main`. `make check-security-scan` MUST fail when
either trigger is re-added.

#### Scenario: a push or pull-request trigger is refused

Given the scan workflow with a `push:` trigger added back under `on:`,
When   `make check-security-scan` runs,
Then   it exits non-zero naming the trigger that must not be there.

- **Test:** `tests/test_security_scan.py::test_the_scan_is_never_a_pr_or_push_check`

#### Scenario: the shipped workflow is a daily pipeline

Given this repository's `.github/workflows/security-scan.yml`,
When   `make check-security-scan` runs,
Then   it exits 0 with both triggers absent and the schedule present.

- **Test:** `tests/test_security_scan.py::test_the_policy_and_digests_are_sane`

### Requirement: Enforcement is data, scoped to the events that may gate

`data/security-policy.json` MUST carry `enforce_events`, and `security_scan.verdict` MUST apply the
`fail_on` policy only for an event in that list. Any other event MUST be report-only — findings are
counted and printed, and the run exits 0.

#### Scenario: an event that may not gate reports only

Given the reports that failed run 40525155122 (a critical `certifi`, two highs),
When   the verdict runs for `push` or `pull_request`,
Then   it exits 0 and prints the findings as reported, not blocking.

- **Test:** `tests/test_security_scan.py::test_an_event_outside_enforce_events_is_report_only`

#### Scenario: the scheduled run still gates

Given the same reports,
When   the verdict runs for `schedule`,
Then   it exits 1 and names every blocking finding.

- **Test:** `tests/test_security_scan.py::test_the_scheduled_run_still_gates`

#### Scenario: a policy that would gate a push is refused

Given `enforce_events` containing `push` (or `pull_request`, an unknown event, or nothing at all),
When   `make check-security-scan` runs,
Then   it exits non-zero naming the offending entry.

- **Test:** `tests/test_security_scan.py::test_check_refuses_a_policy_that_gates_a_push`

### Requirement: The floor is the maximum of the minimums the scanner names

`security_bumps.floors` MUST derive, per package, the lowest fixed version that clears every
advisory the scanner reports for it — that is, the maximum over that package's advisories of the
lowest fixed version above the installed one. A finding without a fixed version MUST NOT become a
floor, and no version may be invented: every floor value comes from the report.

#### Scenario: two advisories on one package take the higher minimum

Given `urllib3` at `2.7.0` with fixes `2.8.0` and `2.9.0`,
When   the floors are derived,
Then   the floor is `urllib3>=2.8.0` — one line that clears both.

- **Test:** `tests/test_security_bumps.py::test_the_floor_is_the_maximum_of_the_minimums`

#### Scenario: an advisory with no fix is not a floor

Given a critical finding whose `fixed` is empty,
When   the floors are derived,
Then   no floor is written for that package.

- **Test:** `tests/test_security_bumps.py::test_a_finding_without_a_fix_is_not_a_floor`

### Requirement: The floor is applied through the ONE generator, never by hand

`make security-bumps` MUST write `tools/security-floors.in`, then regenerate both compiled files by
calling `make -C tools generate-requirements` and `make -C tools generate-requirements-dev`. It MUST
NOT edit a compiled `requirements*.txt`.

#### Scenario: the compiled pins are regenerated, not edited

Given a floor the pinned `tools/requirements.txt` does not satisfy,
When   `make security-bumps` applies it,
Then   `tools/security-floors.in` carries the floor and both compiled files were regenerated by the
generator (the recorded `make` invocations prove it).

- **Test:** `tests/test_security_bumps.py::test_apply_regenerates_the_compiled_pins`

#### Scenario: a dry run writes nothing

Given a floor that is not yet pinned,
When   `make security-bumps DRY=1` runs,
Then   it prints the floor and the pins it would move, and no file is written.

- **Test:** `tests/test_security_bumps.py::test_a_dry_run_writes_nothing`

### Requirement: One bump PR closes the issues it fixes

When the regenerated pins satisfy every floor, `make security-bumps` MUST open or update ONE PR on
the `fix/security-floors` branch whose body carries `Issue:`, `Fix:`, `Benefit:` and `Technical:`
and a `closes #<n>` line for every tagged issue it fixes. When a floor is still unsatisfied after
regeneration it MUST open no PR and exit non-zero.

#### Scenario: the bump PR closes the matched issues

Given scan reports whose findings match two open tagged issues,
When   `make security-bumps` succeeds,
Then   the PR body closes both and names the floor file.

- **Test:** `tests/test_security_bumps.py::test_the_pr_body_closes_the_matched_issues`

#### Scenario: an unsatisfiable floor opens no PR

Given a floor the resolver cannot reach,
When   `make security-bumps` runs,
Then   it reverts, opens no PR, and exits non-zero.

- **Test:** `tests/test_security_bumps.py::test_an_unsatisfied_floor_after_regeneration_opens_no_pr`

### Requirement: The committed floor is a checked gate

`make check-security-bumps` (inside `make ci-unit`) MUST fail when a floor line is malformed or
carries no advisory reason, when a pinned compiled version is below its floor, or when the
`-c security-floors.in` include is missing from `tools/requirements.in` or
`tools/requirements-dev.in`.

#### Scenario: a pin below its floor fails the gate

Given a floor of `urllib3>=2.8.0` and a compiled pin of `urllib3==2.7.0`,
When   `make check-security-bumps` runs,
Then   it exits non-zero naming the package and both versions.

- **Test:** `tests/test_security_bumps.py::test_a_pin_below_its_floor_fails_the_gate`

### Requirement: Renovate owns freshness, and CI keeps the single merge authority

`renovate.json` MUST configure the `pip_requirements`, `pip-compile`, `dockerfile` and
`github-actions` managers, group updates by ecosystem, ignore the generated engine
dockerfiles/params and the vendored registry, and MUST NOT set a top-level `automerge: true` or
`platformAutomerge: true`.

#### Scenario: a config that would bypass CI's merge job is refused

Given a `renovate.json` with `automerge: true` at the top level,
When   the config test runs,
Then   it fails naming the key.

- **Test:** `tests/test_renovate_config.py::test_no_top_level_automerge`
