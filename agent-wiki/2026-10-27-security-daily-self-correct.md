# The scan is its own daily pipeline, and it fixes what it reports

Issue: [#738](https://github.com/asimov-agent/llgenie/issues/738) · implements
[#718](https://github.com/asimov-agent/llgenie/issues/718) · defers
[#739](https://github.com/asimov-agent/llgenie/issues/739) · PR: #740

## What was wrong

`.github/workflows/security-scan.yml` carried `pull_request:` and `push:` triggers, so the scan was a
check on every PR and every merge to `main`. Run 40525155122 (a **push**) failed `make
security-verdict` with `MODE=full` on 8 findings: `certifi` (critical), `filelock`, `urllib3` ×2.
Every one is a **transitive** pin in the generated `tools/requirements*.txt`. Nothing in the
repository could move them — #717's bot edits only a direct pin in `tools/requirements*.in` and
refused all of them, and no Renovate config existed — so the same job would be red on every push
forever. A gate that cannot go green is not a gate.

## Decisions

- **Own pipeline, enforced by data and by a gate on the workflow file.** The scan triggers only on
  `schedule` (04:05 UTC) and `workflow_dispatch`. Enforcement moved from a workflow literal into
  `data/security-policy.json` as `enforce_events: ["schedule", "workflow_dispatch"]`;
  `security_scan.mode_for(event)` applies `fail_on` only for an event in that list and is report-only
  otherwise. `make check-security-scan` fails when `push`/`pull_request` is in `enforce_events`, when
  the list is empty or unknown, **and** when either trigger reappears in the workflow — the rule is a
  check, not a comment.
- **The floor is the maximum of the minimums.** A package can carry several advisories; the one
  version that clears all of them is the highest of their lowest fixed versions. `security_bumps`
  derives that per package from the reports' own `fixed` values; a finding with no fix is never a
  floor, and a "fix" at or below the installed version is ignored (no invented downgrade).
- **One generator, no hand edits.** The floor is written to `tools/security-floors.in`, a pip-compile
  constraint file that `tools/requirements.in` and `tools/requirements-dev.in` include with
  `-c security-floors.in`; both compiled files are then regenerated by `make -C tools
  generate-requirements` / `generate-requirements-dev`. `make check-security-bumps` fails on a pin
  below its floor, a floor line with no advisory reason, or a missing include.
- **Green or nothing, and it closes its issues.** One commit on `fix/security-floors`, one PR whose
  body carries `Issue:/Fix:/Benefit:/Technical:` and `closes #<n>` per matched tagged issue. A
  regeneration that cannot reach the floor, or a red fast gate, reverts and opens no PR.
- **Renovate owns freshness (#718), CI owns the merge.** `renovate.json` groups by ecosystem and
  carries **no** automerge key at all: the repository's `auto-merge` job stays the single merge
  authority. `pip_requirements` bumps re-run the generator through `postUpgradeTasks`, which is why
  the workflow runs the CLI on the runner (`npx renovate@46.3.10`) instead of inside an action
  container that has no docker.
- **Affected images rebuild through the tags they already have.** A base change moves every engine
  tag because the generated Dockerfile embeds `FROM llgenie/base-<backend>:<content hash>`, and a
  Python pin change moves the test image's lockfile hash — so a bump starts the engine-image /
  ci-images jobs without a second list. That is asserted in `tests/test_renovate_config.py` (the
  ignored generated paths) rather than re-implemented.

## Verified

- `tests/test_security_bumps.py` — the maximum-of-the-minimums, no-fix and stale-fix cases, a real

## Why the pin bump is NOT in this PR

The mechanism was proven locally against the real reports: the floors resolve through the real
`pip-compile` to `certifi 2026.10.23`, `filelock 4.2.4`, `urllib3 2.8.0` — and shipping that here
turned `ci-images` and `install-published-*` red, because a **fork** PR's token cannot write the
organisation's packages (`denied: installation not allowed to Write organization package`, #155), so
the new test-image tag the bumped lockfile needs is never published. The bump therefore belongs to the
daily run, whose branch is pushed from THIS repository by `BUMP_TOKEN` and whose PR can publish.
Filed the fork gap as its own issue rather than widening this change; the floors file ships empty and
`make security-bumps` fills it on the next scheduled (or manually dispatched) run.
